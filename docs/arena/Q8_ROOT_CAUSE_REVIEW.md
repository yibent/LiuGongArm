# Q8 根因复盘与修改顺序

2026-09-07，审查版本 `4ff69fc`，BusAgent 子模块 `c0ed3e7`。本次是对当前代码和既有试验的复盘，没有重新运行收费模型或修改云端运行逻辑。监督 LLM 保持关闭。

## 结论

当前系统已经接通多个模型、Bus 事件和若干动作，但尚未把它们组织成可靠的长任务执行闭环。单件成功依靠的目标选择、格网记忆续接、抓法选择、失败诊断和阶段推进，仍有一部分由测试者在系统外完成。继续逐个调阈值或换模型，无法解决这些职责缺失。

Q8 暴露了四个互相放大的缺口：持续场景状态不完整、任务条件未形成统一可计算契约、抓放规划与失败恢复割裂、调度依赖监督 LLM。此前把组件接通和少数成功轨迹当作继续叠加长任务的基础，验证顺序不合理，导致重复花费在同一类断点上。

## 证据与因果

### 1. 监督 LLM 被同时当作任务编排器

`BusAgent/backend/src/apps/desktop-robot/intelligence/task-engine.ts`：

- `acceptDecision` 对复杂规划只保存 `goal.proposal`，转入 `review`；之后依赖 supervisor 将其变成实际 steps。
- `tick` 在复杂任务的当前 steps 执行完后无条件进入 `review`，依赖 supervisor 决定下一段。
- `supervisorEnabled=false` 时 review 停留等待。这既关闭了监督推理，也切断了上述复杂任务的队列生成和阶段展开。

这不是关闭监督后的偶然故障，而是此前就存在的职责耦合。用户关闭的是监督模型，正常调度和可计算的阶段推进应该继续。人工直接调用 Arena 验证组件也没有补齐 Bus 内部这条链路。

### 2. 观察记录没有形成持续更新的场景状态

`source/mr_liu/arena/observed_scene.py` 的 `ObservedScene.update` 只处理 collection；单目标识别、grasp、place_held 和释放结果不会统一更新此对象集合。跨次集合关联主要依靠 25 mm 以内的位置距离，没有把持物运动、容器成员、任务保留的格位等纳入共同状态。

存在独立的视觉引用、格网记忆、持物记录和 Bus scene，但它们没有统一的更新规则。后果包括：

- 看图框出同一个箱子，却因生成了新的引用而未用到旧格网记忆。
- 主相机被手臂遮挡后，没有稳定的对应关系去另一相机继续观察同一目标。
- 重观察会重新计算行列方向；行列与观察相机有关，不能直接跨视角替换编号。
- 物体从桌面移到夹爪、再到格位，任务层缺少统一的对象生命周期和容器成员状态。

实例证据：`pack-model-slot-repair.json` 已抓稳，但主视角找不到箱子；测试者改从侧图定位同一格位后 `pack-side-resume-place.json` 成功。`clearance-fallen-repair-grid.json` 重新框选格网不确定，改用已有格网引用并确认当前几何后，`clearance-retained-fallen.json` 成功。改变的是信息续接方式，并非任务本身不可执行。

### 3. 能生成姿态，不等于已经有可完成任务的操作技能

`source/mr_liu/arena/runtime.py`：

- `_pick_place` 先选抓姿和抬升，后面才进入放置规划。虽已将端点条件用于抓姿排序，仍未验证从该抓姿到目标释放的完整可行性。
- `move` 使用笛卡尔插值和 Arena IK，实际失败后最多尝试若干姿态。当前执行路径没有完整的整臂及持物碰撞轨迹规划。
- `oriented_place_held` 没有候选时只报告“需要重新抓取”，没有可执行的临时放置、换抓、重新检查端点的通用恢复技能。
- `cascade.py` 对不少运动 RuntimeError 执行 fast → models；带朝向的增强放置仍进入同一个 `oriented_place_held`，更换后端标签不一定更换了导致失败的方法。

这是“抓起后卡住”的主要结构性原因之一。之前人工的抬高、转腕、暂放、重新抓取成功，只证明存在一条人工找到的路径，未证明系统会规划它。

模型接入边界也需要重新说明：

- Arena 的官方定位是可组合的场景、机器人与任务/策略评测框架；当前项目实际使用 `PandaTask(NoTask)` 加自定义判定和官方 Panda IK，没有自动获得完整工业操作策略。[官方仓库](https://github.com/isaac-sim/IsaacLab-Arena)
- GraspGenX 的官方端到端例子另接 cuRobo 做碰撞轨迹规划，并在物理仿真中评估执行。其示例使用完整物体网格点云，不能把示例效果直接当作本项目部分 RGB-D 点云输入的成功保证。[官方端到端说明](https://github.com/NVlabs/GraspGenX/blob/main/end2end/README.md)
- AnyPlace 官方流程使用语义粗定位、目标区域裁剪和待放物体完整点云；本项目给其低层接口的是部分 RGB-D 点云。这个输入差异还没有独立充分验证。带端点约束的当前执行分支直接使用自定义旋正几何，不能把这些成功归功于 AnyPlace。[作者项目页](https://any-place.github.io/)

### 4. 任务完成条件与失败恢复仍大量依赖文字推理

Bus `types.ts` 的 `completion` 是字符串，动作参数是开放 record。底层已有朝向/格位评测，但任务层没有统一表达并持续维护“指定区域的所有目标、闭口端向上、正确入格、满箱后再搬、搬运不掉件”等条件。

`failure.py` 已有分类，但部分分类仍从错误字符串提取，`suggested_recovery` 多为建议文本。任务引擎把失败和检查不确定主要归到 review，而非交给一组有输入、效果和验证条件的本地恢复动作。

因此：图像 unknown、实际放错、当前抓法不可用、模型服务超时虽然含义不同，仍容易交给 LLM 从长记录中重新解释；正常进度无法由可计算状态稳定推进。

### 5. 性能有两个独立瓶颈

既有 `repair-6` 返回记录：监督占 11 次调用、272,350 输入 tokens。任务编排依赖监督且上下文重复，是高 API 消耗的实证，不应归结为持续把视频喂给 Qwen。

关闭监督后的 `clearance-normal-slot-repair.json` 无 Qwen、无 GraspGenX/AnyPlace 推理，仍耗时 39.36 s。相邻事件时间差显示：旋正运输约 9.34 s、退出约 6.65 s、放置下降约 4.45 s、抓取接近约 4.38 s。这些是阶段墙钟耗时，包含仿真/渲染/控制等开销，尚不是 GPU/CPU profiler 的归因。699 个控制步在 60 Hz 仿真步长下约为 11.65 s 模拟时间；不能把 39.36 s 全部解释为机器人动作本身需要的时间。

所以后续分别量测 LLM/工具往返、物理步进、相机渲染、图像编码和轨迹等待，不能只缩短提示词或调大运动步幅。

## 当前能力边界

| 能力 | 当前证据 |
| --- | --- |
| 检测集合、空间分组、最多区域选择 | 有单项成功，也有误检/漏检；未形成稳定统计 |
| 正常件指定格位放置 | 有 Bus 自然语言单件成功；最新快环组件也成功 |
| 横倒件扶正 | 有人工选择/续接下的物理成功；自主完整恢复未通过 |
| 当前抓法不适合放置时自动暂放换抓 | 人工路径成功，通用自动技能未实现 |
| 倒置件翻正、六格连续装满 | 未通过 |
| 满箱含载搬运与叠放 | 未通过，不能从空箱或单件放置外推 |
| 换布局、数量、物体后的泛化 | 缺独立多变体连续任务验收 |

109 个相关代码测试证明部分接口、几何和状态转移没有已知回归，不能替代上述真实闭环成功率。

## 修改顺序与验收门槛

1. **先拆掉监督与调度的硬依赖。** 规划器已产出的可执行方案由程序落队列；已知依赖和阶段根据状态推进。LLM 监督作为可选事件消费者。人工决策也进入同一 Bus 恢复接口，不再只在 Arena 外部操作。验收：关闭监督时，复杂方案会生成并执行队列；常规成功和可恢复的暂时遮挡不会被送入无人处理的永久 review；此路径监督 API 调用为零。

2. **统一对象、格位、持物和完成条件。** 保留视觉证据，但使用跨观察稳定的对象/容器/格位身份；用 grasp/place 事件更新状态，保留观测来源、时间和不确定性。目标条件由用户意图及当前几何产生，不靠配置资产白名单。验收：换相机、短时遮挡、物体移动、独立抓起再放下，保持目标和格位含义；unknown 导向补充证据而非自动宣布失败或空位。

3. **把抓放和换抓做成有恢复能力的技能。** 抓取候选与最终放置需求一起考虑；接入并验证已有碰撞规划能力，保留 Arena 机器人/执行底座，不自研关节 IK。若一次不可完成，规划受控暂放和再次抓取。先审查 cuRobo 与锁定版本、部分点云、持物几何的兼容性，不能因为官方示例用了它就宣布接入即解决。验收：正常、横倒、倒置、需要换抓各有无人干预成功与受控失败；失败后保留真实持物状态，可从当前现场续接。

4. **收敛回退和状态上下文，再恢复长任务验收。** 本地按失败原因做一次有新信息或新动作的恢复；更复杂的策略变更才请求规划决策。记录实际调用过的后端，排除“标签变了、方法没变”的重复。按任务状态和证据引用形成小上下文，正常动作不等待监督 LLM。

5. **用同一套系统跑多个变体。** 将 Q8 作为基准之一；先跑单技能变体和故障注入，再从一条自然语言指令完成装满、含载搬运和叠放。改变位置、数量、端面朝向、料箱姿态、照明和短时遮挡；报告人工介入次数、成功率、恢复原因、墙钟耗时和模型调用。诊断时可以人工给目标，但最终验收禁止测试者选框、换引用或手动接步骤。

后续每项修改必须说明它解决上述哪条断点、替换了哪段旧逻辑、通过了哪种变体。停止把“某一个摆法又成功一次”作为架构已经闭环的依据。
