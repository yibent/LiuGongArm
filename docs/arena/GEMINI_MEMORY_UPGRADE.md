# Gemini 与 BusAgent 记忆节点升级

部署日期：2026-09-07。适用于 `codex/arena-panda-grasp-place`。

## 运行配置

- 规划、监督、短上下文视觉选择、旧语义理解入口统一读取模型配置。默认 `gemini-3.7-flash`，备用 `gemini-3.8-flash`；`peerGroup=gemini-flash` 使切换首选后仍能反向互备。
- 两个用户指定网关使用 OpenAI 兼容的 `/v1/chat/completions`。模型名称是网关实际接受的 ID，不据此推断网关底层实现。
- 失败请求不重放机械臂动作；一次推理内跳过失败接口，跨请求冷却 30–120 秒。保留原工具调用消息及供应商扩展字段，支持工具结果续接。
- 前端模型设置支持 Gemini、地址、密钥、角色、备用模型、思考强度和按需读图。密钥仅保存在服务器权限为 0600 的配置中，不返回浏览器或提交到仓库。
- 对话模型配置及 ASR/TTS 环境文件保留。用户随后要求开启自动监督器，已设为 `supervisorEnabled=true`；规划和监督仍是独立 BusAgent 智能体，使用各自提示词。原有全局暂停保持。

## 原生框选进入实际视觉链路

```text
任务规划 / 语义定位请求
  → 简单识别继续使用现有快环
  → 需要复杂语义时 locate_object，或 read_image + ground_region
  → Gemini box_2d [ymin,xmin,ymax,xmax]，整图坐标 0..1000
  → 转换为 [left,top,right,bottom]，0..1
  → 绑定 snapshot_ref 和 camera
  → 原快照 SAM2 分割 → 光流重定位 → 当前帧 SAM2 精化
  → RGB-D 目标点云、稳定物体引用 → 原抓放执行接口
```

模型返回无目标、无效框或互相矛盾的坐标时不会伪造物体引用。视觉选择只携带一帧和目标描述，输出预算 1536 token；图像不默认加入规划历史。现有 YOLOE、SAM2、SAM3、光流与 Florence 本地模型继续使用。

本次启用的是原生检测框。掩码由 SAM2 生成；尚未启用 Gemini 原生分割掩码，也未把 UI 元素坐标当作机械臂三维目标。网关能力和耗时需实际验证，不能假设所有 Gemini 接口都暴露相同功能。坐标约定参考 [Google 图像理解文档](https://ai.google.dev/gemini-api/docs/image-understanding)，兼容协议参考 [Google OpenAI 兼容文档](https://ai.google.dev/gemini-api/docs/openai)。

## 记忆和上下文压缩

- `robot.memory` 消费用户输入、回复和执行结果，将不可变 Bus 事件归档物化为会话记忆；发布 `memory.updated`。
- `robot.context_compression` 异步消费该事件，为规划和对话的实际预算生成本地抽取式视图；发布 `context.compacted`，记录预算、估算大小、省略数量，`model_calls=0`。
- 记忆和压缩视图写入 MySQL。缓存使用会话、预算、内容版本匹配；任务队列和持物状态每次重新读取。新事件尚未被记忆节点处理时直接读取归档，不等待异步节点，也不返回旧缓存。
- 原始对话、完整任务和工具证据仍可通过 `read_history` / `read_evidence` 查询。用户要求、助手说法、执行证据分开表示；不会把“助手说成功”转成物理成功。
- 模型工具循环由同一压缩服务创建有预算的 `InferenceWindow`，按完整工具调用组压缩，保留原始证据索引。
- 任务摘要显式提供全局暂停、完整任务总数、各状态数量及列表范围，避免把过滤或压缩后的列表长度误报为总任务数。历史游标按数据库 UTC 时间处理。

## 验证

- 后端全量测试 299 项通过；最后的时间游标和队列摘要修正另跑相关测试 45 项通过。后端构建、修改代码 lint、前端类型检查及生产构建通过。
- 两条网关的文本请求和真实画面原生框选均成功；3.7 的工具结果续接成功。
- 3.7 实际选框耗时约 8.25 秒；后续感知命令约 0.67 秒，得到蓝色料箱引用、16,000 个 RGB-D 点，SAM2 掩码评分 0.984375。评分是模型输出，不能等同于抓放成功率。
- 3.8 独立框选复测约 4.75 秒。前面的请求出现过超时；这些是单次样本，不能作为延迟保证或综合基准。
- 真实 WebSocket 只读指令依次触发 `intent.created → robot.memory → memory.updated → robot.context_compression → context.compacted`；规划由 `robot.planning` 返回决策。对话先回应“我核对一下当前状态”，收到规划结果后给出具体回答。该查询只调用一次规划模型，没有下发运动步骤。
- MySQL migration 4、会话记忆和 2000/2400/4200 三档压缩视图均在云端实际生成。
- 重启后再次在同一会话查询，能够回忆上一轮检查内容，并区分累计 40 个任务、8 个未结束任务（包含当前查询）与展示的 7 项其他任务。原有 38 个任务保持，测试仅增加无运动步骤的查询记录。
- 第二次查询实际遇到 3.7 请求超时（20 秒），自动切换到 3.8 后完成回答（备用请求约 7.74 秒）。因此互备已在真实规划中验证，但首次遇到网关故障仍有超时等待。`model_calls` 当前统计成功返回的调用；失败尝试单独记录为 `provider_failure`，不能将成功计数当作全部请求数。
- 第二次查询文本回复完成后出现一次 `TTS connection closed before ready`。语音配置未修改；本次未将语音接口可用性认定为已解决。
